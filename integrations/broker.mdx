title: 'Broker'

The Broker is the execution plane over a Connection that already exists. It reads connected data and runs named provider operations inside workspace scope, with authorization, rollout, grants, and audit checks.

The Broker does not connect providers. Start with [integrations and connections](/integrations/overview), then use the Broker through:

- the CLI (`driftless broker ...`);
- REST under `/api/v1/workspaces/:slug/broker`;
- synthesized MCP tools such as `<provider>_records` and `<provider>_document_content`, when the provider is ready and the workspace rollout permits it.

There is no generic `driftless_broker` MCP router. A legacy call with that name is not a public capability. MCP synthesized tools are provider-specific and read-only; they do not expose a generic action, write, or connection-setup surface.

## What it can do

The CLI and REST surface can inspect available operations, run a named read or write operation, read synced records, and materialize supported content. The exact operation set is owned by the connected provider and the workspace's rollout policy. An agent should never invent an operation that the provider does not list.

| Capability | CLI | REST | MCP |
|---|---|---|---|
| Inspect connections and operations | `broker connections`, `broker operations` | Broker connection and operation routes | No generic router |
| Run a named operation | `broker invoke <provider> <operation>` | Broker invoke route | No generic action tool |
| Read synced records | `broker records` | Broker records route | `<provider>_records` when synthesized |
| Read live document content | `broker page` | Broker page-content route | `<provider>_document_content` when synthesized |
| Connect or disconnect a provider | `integration connect` / `integration` | Integration setup routes | Human/CLI setup only |

## Gates and safety

The Broker fails closed when the feature is disabled, the external rollout is closed, the provider operation is not policy-allowed, or the caller has no grant. A listed capability is not automatically usable. A write never inherits authorization from a market search, a CRM read, or a sequence draft.

Every executed operation is workspace-scoped and audited. Writes require the provider's supported idempotency key; Brein does not invent provider guarantees. A failed write must not be blindly retried with a different key.

## Materialization is separate

Reading a provider, reading synced records, and materializing content are different operations:

- a live read asks the provider for bounded data;
- a synced-record read uses the connected mirror;
- materialization creates a Brein-owned object only when the named operation explicitly supports it;
- context retrieval never silently queries a provider.

An external observation does not become a CRM contact or commercial truth merely because the Broker read it. A person still has to be explicitly revealed or imported before entering the contact workflow.
