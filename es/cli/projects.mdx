La familia de comandos `project` opera la superficie de [projects](/es/concepts/projects): un project contiene cards, y un agente recorre el board con `project card next`. Todo comando que corre un agente aquí, un humano también puede correrlo. Agrega `--json` a cualquier comando para salida de máquina.

Las lecturas son **active-only, acotadas y brief por defecto**. `project list` devuelve projects activos en una página acotada y paginada por cursor; `--status all` opta a done/archived. La búsqueda por intención es `project search <intent>`, active-only salvo `--include-archived`. `project get` es brief salvo que pases `--view full`. El ciclo de vida es **explícito**: `close`, `archive`, `restore` y `purge` son comandos separados — `project update` rechaza un `--status` que toque el ciclo de vida.

## Projects

| Comando | Descripción |
|---|---|
| `project add <title>` | Crea un project. Opcional `--goal "..."`, `--playbook <slug>`. |
| `project list [--status active\|all] [--owner me] [--limit n] [--cursor c]` | Lista projects activos en una página acotada; `--status all` opta a done/archived. |
| `project search <intent> [--owner me] [--include-archived] [--updated-after <iso>] [--limit n] [--cursor c]` | Búsqueda por intención sobre título, goal y bodies de cards. Active-only salvo `--include-archived`. |
| `project get <id> [--view summary\|brief\|full]` | Detalle del project; **brief por defecto**, `full` es explícito. |
| `project close <id> [--no-durable-learning]` | Valida la terminación y devuelve un `context_outcome` (idempotente). |
| `project archive <id>` | Retira de forma reversible un project completado. |
| `project restore <id>` | Restaura un project archived a `done`. |
| `project purge <id> --dry-run` \| `--expected-version <n>` | Elimina permanentemente un project archived (owner/admin; version CAS). |
| `project update <id> [flags]` | Actualiza `--title`, `--goal` o `--playbook`. El ciclo de vida va por close/archive/restore. |
| `project cards <id> [flags]` | Lista las cards de un project en orden de board. Filtros: `--status`, `--owner`, `--limit`, `--cursor`. |
| `project apply <id> --file @plan.json` | Aplica un plan declarativo de cards (con `--dry-run`). |

- **`--goal`** define el terminado del project; **`--playbook <slug>`** apunta a un topic de Knowledge que el agente lee para aprender a ejecutar el project (se guarda como `playbook_slug`).
- El status del project es uno de `active`, `done`, `archived`. `list` por defecto es `active`; `search` es active-only salvo que pases `--include-archived`.

## Cards

Las cards se gestionan bajo `project card`. El status de una card es uno de `todo`, `in_progress`, `blocked`, `review`, `done`.

| Comando | Descripción |
|---|---|
| `project card next <project-id>` | El tick del loop: la próxima card accionable más su context bundle. |
| `project card add <pid> --title "..." [flags]` | Crea una card. Ver flags abajo. |
| `project card get <pid> <cid>` | Detalle de la card. |
| `project card update <pid> <cid> [flags]` | Actualiza título, descripción, acceptance, validate, deps, status u owner. |
| `project card status <pid> <cid> <status>` | Mueve una card a un status. |
| `project card move <pid> <cid> <to-project-id>` | Mueve una card a otro project. |
| `project card rm <pid> <cid> [--dry-run]` | Elimina una card `todo`. Rechaza dependientes y Notes de origen; `--dry-run` previsualiza el impacto. |

Los `add` y `update` de card aceptan: `--description "..."` (o `@file`), `--acceptance "..."`, `--validate "cmd"`, `--dep <card-id>` (repetible, setea `depends_on`) y `--owner <member-id>` (se guarda como `owner_clerk_id`).

```bash
driftless project add "Renovación de refunds" --goal "El path de refund es idempotente" --playbook refund-flow
driftless project card add prj_abc \
  --title "Handler de webhook idempotente" \
  --acceptance "Las entregas duplicadas de webhook son un no-op" \
  --validate "npm test -- webhooks" \
  --dep card_setup --owner mem_123
driftless project card next prj_abc                 # card + context bundle
driftless project card status prj_abc card_xyz done
```

`next` elige en orden de prioridad (`in_progress`, luego `review`, luego `blocked`, luego un `todo` ready); un `todo` está ready solo cuando sus `depends_on` están todos en `done`. La verificación es reportar y exponer: la CLI guarda el resultado de `validate`, nunca corre el comando por ti.

## Crear en lote y apply

`project card add --file @cards.json` crea muchas cards de una vez; `depends_on` puede referenciar una card anterior por título o por id. `project apply --file @plan.json` aplica un plan declarativo de project (el plan puede incluir `playbook`).

```bash
driftless project card add prj_abc --file @cards.json
driftless project apply prj_abc --file @plan.json --dry-run
```

## Ciclo de vida: close, archive y purge

`project close`, `project archive`, `project restore` y `project purge` son las únicas formas de mover un project hacia adelante o retirarlo:

```bash
# Close — valida la terminación; destila las write-back Notes una vez; idempotente
driftless project close prj_abc
# context_outcome: created | already_exists | skipped | failed

# Archive — retira un project done (inmutable; solo restore/purge pueden tocarlo)
driftless project archive prj_abc

# Purge — solo owner/admin; previsualiza el impacto, luego confirma con version CAS
driftless project purge prj_abc --dry-run
# impact: { version, cards, context_refs, origin_notes_preserved }
driftless project purge prj_abc --expected-version 7
# purge_outcome: purged | already_absent
```

`close` se rehúsa a correr mientras queden cards que no estén en `done`, y rechaza `--no-durable-learning` cuando sí existen Notes durables. `purge` preserva las write-back **origin Notes** que engendró el project (sobreviven al borrado); se cuentan en `impact.origin_notes_preserved`. Un reintento de `purge` tras borrar el project devuelve `already_absent`, nunca erroriza.

El safe delete de cards sigue la misma forma — `project card rm` solo elimina una card `todo`, **rechaza** cards de las que dependen otras, y **rechaza** cards que llevan write-back Notes de origen (reubícalas primero). `--dry-run` previsualiza los `dependents` y `origin_notes` que la bloquean.

## Flags, archivos y JSON

- **`@file`** lo aceptan `--description`, `--file` (lote de cards) y `apply --file`.
- **`--json`** funciona en cada comando para salida de máquina.
- **`--cursor`** pagina una lista/get acotada; el valor es opaco, viene del `nextCursor` de la página previa.
- Las cards se escanean en busca de secrets al escribir, igual que los topics; pasa `--allow-secrets` solo cuando de verdad quieras guardar uno.

## Permisos

Las escrituras de project y card son acciones de miembro del workspace; **purge es solo owner/admin**. Por MCP las mismas operaciones requieren el scope `work:write`; una API key actúa con el rol del miembro que la creó (una agente faceless no puede purgar). Asignar un owner usa un member id de `driftless member list`.

## Errores

Un `--status` inválido (fuera del enum de card o de project) se rechaza antes de la llamada. Un `--dep` o un `depends_on` de lote que nombra una card desconocida hace fallar la creación. Un `project purge` sin `--dry-run` ni `--expected-version` se rechaza; un `expected_version` equivocado devuelve `409 VERSION_CONFLICT` (re-corre `--dry-run` y reintenta). Un `validate` con salida cero es una convención que corre el agente, no un chequeo del servidor.
