## Los cuatro verbos de documento

Cerebro son documentos markdown en carpetas: un documento es `<carpeta>/<nombre>.md`, la carpeta es un área de conocimiento y `<carpeta>/Structure.md` dice para qué sirve esa área. Estos cuatro verbos son el modelo completo; los comandos con forma de topic de abajo operan sobre exactamente el mismo store.

| Comando | Flags | Descripción | Ejemplo |
|---|---|---|---|
| `context ls [carpeta]` | `--json` | Lista el árbol — carpetas y luego sus documentos (`Structure.md` primero). Omite la carpeta para ver todo. | `driftless context ls billing` |
| `context read <ruta>` | `--json` | Imprime el cuerpo markdown (cuerpo en stdout, encabezado en stderr, así se pipea limpio) | `driftless context read billing/refund-flow.md` |
| `context write <ruta>` | `--content @f\|"md"`, `--title`, `--private`, `--public`, `--dry-run`, `--allow-secrets`, `--json` | Crea o **REEMPLAZA** un documento. Léelo primero si ya existe. Una carpeta desconocida crea el área. | `driftless context write billing/refund-flow.md --content @doc.md --title "Refunds"` |
| `context search "<q>"` | `--folder <f>`, `--limit <n>`, `--json` | Busca documentos; imprime `ruta · título` + un snippet por hit | `driftless context search "idempotency" --folder billing` |

Un documento nace compartido en el workspace: no hay nada que aprobar. `--private` lo guarda solo para ti y `--public` lo devuelve al equipo (`is_private` en la API/MCP); `context add --private` hace lo mismo al crear. Mira [Visibilidad y compartir](/es/concepts/governance).

## Listar y buscar

| Comando | Flags | Descripción | Ejemplo |
|---|---|---|---|
| `context list` | `--stale`, `--repo`, `--tag <name>`, `--docs`, `--auto`, `--manual`, `--limit <n>`, `--all`, `--json` | Lista topics con filtros. Por defecto muestra los **40 más relevantes** (los drifteados primero); imprime `Showing N of M`. Usa `--all` / `--limit N` para ver más (`--json` no tiene tope). `--tag` se puede repetir (semántica OR), así puedes listar una categoría entera. | `driftless context list --tag billing` |
| `context get <topic>` | `--json` | Detalle completo del topic | `driftless context get b2b-guard` |
| `context get --files` | `--files "a,b"`, `--json` | Empareja topics con archivos | `driftless context get --files "src/auth/guard.ts"` |
| `context get --diff` | `--json`, `--mark` | Topics para los cambios actuales | `driftless context get --diff` |
| `context get --diff --mark` | `--mark` | …y marca como **drifted** los topics que coinciden desde git local | `driftless context get --diff --mark` |
| `context search` | consulta, `--tag <name>`, `--json`, `--include-notes` | Búsqueda de texto completo **ordenada por relevancia** (top 50; las coincidencias de nombre/título quedan más arriba). Admite `"frases entre comillas"`, `OR`, `-negación`. Acota con más términos en vez de paginar. `--tag` (repetible, OR) limita la búsqueda a una categoría. Los documentos privados quedan fuera salvo que uses `--include-notes`. | `driftless context search "refunds" --tag billing` |

## Tags: el registro de categorías

Los tags son categorías a nivel de workspace a las que se anclan los topics. Los nombres se normalizan en todas partes (minúsculas, los espacios pasan a guiones), así que `Billing` y `billing ` son el mismo tag. Adjuntar un tag que nunca se creó de antemano lo **registra automáticamente**. El registro es curaduría, nunca una barrera.

| Comando | Flags | Descripción | Ejemplo |
|---|---|---|---|
| `tags` | `--limit <n>`, `--offset <n>`, `--json` | Lista el registro con la cantidad de topics por tag (paginado, los más usados primero) | `driftless tags` |
| `tags add <name>` | `--description "..."` | Crea un tag de antemano (idempotente: volver a agregarlo fusiona la descripción) | `driftless tags add billing --description "Reglas de facturación"` |
| `tags rename <old> <new>` | ninguna | Renombra en todas partes, reescribiendo cada topic que lleve el tag (owner/admin) | `driftless tags rename billing facturacion` |
| `tags rm <name>` | ninguna | Elimina del registro **y** desvincula de cada topic (owner/admin) | `driftless tags rm legacy` |

## Crear y actualizar

| Comando | Flags | Descripción | Ejemplo |
|---|---|---|---|
| `context add` | `--what`, `--how`, `--content`, `--pattern`, `--tags`, `--rel`, `--where`, `--decisions`, `--gotchas`, `--ownership`, `--status`, `--file`, `--dry-run` | Crea un topic | `driftless context add "payment-flow" --content "# Flujo de pago\n\n## Qué\nCheckout de Stripe" --pattern "src/billing/**"` |
| `context update` | `--what`, `--how`, `--content`, `--gotcha`, `--decision`, `--invariant`, `--check`, `--enforce`, `--add-pattern`, `--remove-pattern`, `--tags`, `--status`, `--where`, `--decisions`, `--gotchas`, `--ownership`, `--pattern`, `--rel`, `--dry-run`, `--json` | Modifica un topic | `driftless context update payment-flow --gotcha "Se requieren idempotency keys" --add-pattern "src/webhooks/stripe/**"` |
| `context delete` | `--dry-run`, `--json` | Elimina un topic | `driftless context delete payment-flow --dry-run` |
| `context merge` | `--into`, `--dry-run`, `--json` | Funde un duplicado en el que sobrevive (archiva el origen; la prosa nunca se fusiona) | `driftless context merge payment-flow-2 --into payment-flow --dry-run` |
| `context move` | `--to <workspace>`, `--dry-run`, `--json` | Reubica un topic en otro workspace al que perteneces | `driftless context move payment-flow --to acme-platform` |

## Validación de patterns

Cada `--pattern` y `--add-pattern` se valida contra tu checkout local antes de la llamada a la API:

| Resultado | Significado |
|---|---|
| `✓ pattern "src/auth/**" matches 12 files` | Anclaje sano |
| `⚠ over-broad anchor` | Coincide con más de 100 archivos; considera dividir el topic |
| `✗ pattern matches 0 files` | Bloqueado; corrige el glob o usa `--where` para una ruta explícita |

## Enlaces y salud

| Comando | Flags | Descripción | Ejemplo |
|---|---|---|---|
| `context link` | `--dry-run`, `--json` | Vinculación entre repos | `driftless context link payment-flow` |
| `context doctor` | `--json` | Audita la salud del contexto | `driftless context doctor` |
| `context relations` | `--json` | Lista las relaciones tipadas | `driftless context relations payment-flow` |
| `context graph` | `--depth N`, `--json` | Grafo de relaciones entre topics | `driftless context graph payment-flow --depth 2` |

`context doctor` audita la capa de topics buscando zombis (patterns que coinciden con cero archivos), huérfanos (repo eliminado), stale y documentos delgados (`draft`) — `status` es inerte, no un estado de gobernanza.

## Compatibilidad (no-op)

La gobernanza Nota→Knowledge está **retirada**. Estos comandos siguen en la superficie para que un agente o script viejo reciba una respuesta en vez de un error: cada uno imprime *"Los documentos de Cerebro no necesitan aprobación; edítalos con `driftless context write`."* y sale con 0. No los llames — para cambiar un documento, reescríbelo. Mira [Visibilidad y compartir](/es/concepts/governance).

| Comando | Descripción | Ejemplo |
|---|---|---|
| `context propose <topic>` | No-op | `driftless context propose payment-flow` |
| `context approve <topic>` | No-op | `driftless context approve payment-flow` |
| `context reject <topic>` | No-op | `driftless context reject payment-flow` |
| `context archive <topic>` | No-op | `driftless context archive payment-flow` |
| `context ack <topic>` | No-op | `driftless context ack payment-flow` |
| `context unvouch <topic>` | No-op | `driftless context unvouch payment-flow` |
| `context pr <topic>` | No-op (las ediciones sugeridas están retiradas) | `driftless context pr payment-flow` |
| — | Para cambiar un documento: léelo, integra el hecho nuevo y escríbelo de vuelta | `driftless context write billing/refund-flow.md --content @doc.md` |

## Compartir

| Comando | Descripción | Ejemplo |
|---|---|---|
| `context share <topic>` | Enlace público de solo lectura (`--revoke` para desactivarlo) | `driftless context share payment-flow` |

## Workspaces

Un workspace es el contenedor de más alto nivel para el contexto; puedes pertenecer a varios y cambiar entre ellos sin volver a autenticarte. Un solo `driftless login` registra cada workspace al que perteneces bajo una única [key con alcance](/es/concepts/workspaces#credenciales-acotadas).

| Comando | Descripción | Ejemplo |
|---|---|---|
| `workspace list` | Los workspaces a los que perteneces (● = activo) | `driftless workspace list` |
| `workspace current` | El workspace activo | `driftless workspace current` |
| `workspace switch <slug>` | Opera sobre otro (sin volver a iniciar sesión) | `driftless workspace switch acme-platform` |
| `workspace add --key <drift_…>` | Registra un workspace con su API key | `driftless workspace add --key drift_…` |
| `context move <topic> --to <slug>` | Reubica un topic en otro workspace | `driftless context move payment-flow --to acme-platform` |

`context move` reubica el documento y requiere owner/admin en el origen más membresía en el destino. Mira [Workspaces](/es/concepts/workspaces).

## Más allá del contexto: el resto del workspace

Todo el workspace es headless, no solo los topics. La misma CLI maneja las superficies de trabajo, y un agente corre los comandos que correría una persona:

| Familia | Comandos | Docs |
|---|---|---|
| **Collections y records** | `collection list\|get\|records`, `collection record add\|update` | [Collections](/es/concepts/collections) |
| **Áreas** | `area list\|add\|rename\|rm`, más `context add/update --area` | [Áreas](/es/concepts/areas) |
| **Documentos y visibilidad** | `note add`, `context write`, `context share` | [Visibilidad y compartir](/es/concepts/governance) |
| **Miembros** | `member list\|invite\|role\|rm\|invites` | [Workspaces](/es/concepts/workspaces#invitaciones) |
| **Market data** | `market capabilities\|suppliers\|opportunities\|awards\|risks\|permits` | [Market Data](/es/api/market-data) |

Corre `driftless <family> --help` para ver el conjunto completo de flags.
