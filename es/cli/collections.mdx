La CLI expone el sustrato operacional Collection/Record. En el producto comercial actual, un Record es una persona que el workspace adquirió y archivó explícitamente; no uses esta página como permiso para crear una cuenta de empresa desde evidencia de mercado.

## Inspecciona Collections

```bash
driftless collection list
driftless collection get <collection-id> --view full
driftless collection records <collection-id> --limit 25
```

Las lecturas son acotadas. Sigue el cursor devuelto en vez de asumir que una página está completa. Usa `--json` para salida de máquina.

## Trabaja un Record de contacto existente

```bash
driftless collection record update <collection-id> <record-id> \
  --status contactado \
  --fields '{"next_action":"Responder con la oferta revisada"}'
```

El estado debe coincidir con el lifecycle configurado de la Collection. `history` y `schedule_activity` son operaciones explícitas separadas.

## Archiva una persona adquirida

Para un flujo CRM customer-facing, un contacto revelado o importado se archiva mediante el camino de personas/contacto y la Collection de contactos adecuada. Los comandos de bajo nivel de Collection no convierten accidentalmente una empresa, licitación, adjudicación o proveedor en un Record de contacto; usa el camino actual de contacto adquirido y verifica su resultado.

## Lifecycle

`archive` y `restore` son explícitos y reversibles. `purge` es permanente, sólo owner/admin y debe previsualizarse con el contrato actual de dry-run/version antes de ejecutarse. El borrado de un Record también es una operación separada; nunca lo confundas con cambiar un estado.

## MCP y REST

La superficie MCP pública usa `collection_query`, `crm_record`, `crm_collection` y `people_file`. No usa las tools genéricas retiradas `driftless_collection` o `driftless_entity` como contrato para integraciones nuevas. REST y CLI pueden conservar rutas de compatibilidad de bajo nivel para consumidores técnicos activos.
