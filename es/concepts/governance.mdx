---
title: 'Visibilidad y compartir'
description: "Un documento de Cerebro nace compartido en el workspace. Privado es un toggle por documento, el enlace público es un comando, y no hay nada que aprobar."
---

Cerebro son **documentos markdown en carpetas**. Un documento **nace compartido en el workspace**: no hay cola de revisión, ni aprobación, ni eje Nota-vs-Knowledge. La única confianza es que está en Cerebro. Lo que antes era gobernanza son ahora dos cosas mucho más pequeñas: quién puede ver un documento y quién puede cambiarlo.

## Un documento nace compartido

Hay una sola primitiva, el **documento**: `<carpeta>/<nombre>.md`, donde la carpeta es un área de conocimiento y `<carpeta>/Structure.md` dice para qué sirve esa área. Lo escribes y ya es del equipo: visible para cada miembro del workspace, recuperable por cada agente, de inmediato.

```text
context write  →  el documento está en Cerebro  →  todo miembro y agente lo lee
```

- **Compartido** (el default): todo miembro del workspace lo ve, la búsqueda lo devuelve, `context_retrieve` lo rankea.
- **Privado** (`--private` en la CLI, `is_private` en la API/MCP): un toggle por documento. Solo lo ve quien lo escribió y queda fuera de la búsqueda hasta que lo comparta. Es un interruptor, no una etapa de la que haya que graduarse — `--public` lo devuelve.
- **Enlace público**: una URL de solo lectura que cualquiera abre sin iniciar sesión. Opt-in por documento y revocable en cualquier momento.

No hay `proposed`, ni `reviewed`, ni cola de aprobación. El campo `status` sigue existiendo en el contrato y es **inerte**: nada lo lee como autoridad.

Para cambiar un documento, léelo y reescríbelo. `context write` reemplaza el cuerpo entero, así que el movimiento honesto es leer → integrar el hecho nuevo → escribir de vuelta.

```bash
driftless context read billing/refund-flow.md > refunds.md
driftless context write billing/refund-flow.md --content @refunds.md
driftless context write billing/refund-flow.md --content @refunds.md --private
driftless context share refund-flow            # enlace público de solo lectura
driftless context share refund-flow --revoke   # revocarlo
```

## La superficie del cliente

La superficie documental customer-facing del dashboard es **Cerebro**: el árbol de carpetas y sus documentos markdown. El CRM comercial es una superficie separada y centrada en contactos bajo Prospectos. Los comentarios y el grafo de topics retirado no forman parte de la navegación actual del cliente.

## Quién puede cambiar qué: roles del workspace

La membresía es lo que da acceso. Cada miembro tiene un rol:

| Rol | Puede |
|---|---|
| `member` | Leer todo documento compartido + escribir y reescribir documentos |
| `admin` / `owner` | …+ administrar miembros, mover documentos entre workspaces y borrar |

Escribir no está restringido: un miembro escribe y reescribe documentos directamente. Solo un `owner` puede otorgar o revocar el rol `owner`, y al último owner no se le puede degradar ni quitar. Quien crea el workspace es el primer owner; administra roles en **Settings → Members**.

Los permisos controlan **visibilidad y administración, nunca el código**. Driftless informa; jamás le impide a alguien escribir código.

## Qué lee el agente

El agente ya no pondera un nivel de confianza: lee lo que hay. Cada `context get` sigue trayendo la identidad del documento y su frescura, que es lo que de verdad importa:

```json
{
  "classification": { "status": "draft" },
  "stale": { "is_stale": true, "stale_reason": "anchored code changed" }
}
```

Trata `stale` como la señal sobre la que sí vale actuar: el documento era cierto y el código se movió. `status` es un campo histórico; ignóralo.

## Retirado: la gobernanza Nota → Knowledge

`propose`, `approve`, `reject`, `archive`, `ack`, `unvouch` y `pr` (Suggested edits) están **retirados**. Siguen en el CLI y en la API como **no-ops** para que un agente o script viejo reciba una respuesta clara en vez de un error, y todos imprimen la misma línea antes de salir con 0:

```bash
driftless context propose <slug>   # → Los documentos de Cerebro no necesitan
driftless context approve <slug>   #   aprobación; edítalos con
driftless context pr <slug>        #   `driftless context write`.
```

No los llames. Si un documento tiene que cambiar, reescríbelo: ese es el flujo completo ahora, y es el mismo seas persona o agente.

## Por qué es determinista

Nada de esto es menos auditable. Cada escritura sube la versión y agrega un evento de historial: quién escribió, cuándo y qué cambió. Un CTO todavía puede responder *"¿por qué el agente confió en esto?"* con un registro preciso; ese registro simplemente ya no incluye un paso de aprobación que nadie estaba corriendo.

<Note>
Los documentos que eran `reviewed` antes del retiro conservaron su contenido y su historial; solo desapareció la insignia. Nada se archivó ni se borró en la migración.
</Note>
