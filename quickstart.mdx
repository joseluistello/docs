Driftless starts with topics — durable engineering memory created by humans and agents. No repo scan required.

## Prerequisites

- Node.js 22 or later
- A Driftless workspace at [driftless.icu](https://driftless.icu)

<Steps>
  <Step title="Install the CLI">
    ```bash
    npm install -g @driftless-sh/cli
    ```

    ```bash
    driftless --version
    ```
  </Step>

  <Step title="Log in">
    Authenticate from the terminal:

    ```bash
    driftless login
    ```

    For CI or non-interactive setup, pass an API key from the dashboard:

    ```bash
    driftless login --key drift_your_api_key_here
    ```

    <Tip>
      Store your key as `DRIFTLESS_API_KEY` in your environment to skip `--key` on every command.
    </Tip>
  </Step>

  <Step title="Install the agent skill">
    Install Driftless context instructions so coding agents automatically load topics before editing:

    ```bash
    driftless install-skill
    ```

    This writes `AGENTS.md` and `CLAUDE.md` into your repo. Agents will see topic-loading instructions every session.
  </Step>

  <Step title="Create your first topic">
    Start by capturing what you know about a part of your system:

    ```bash
    driftless context add onboarding-context \
      --kind domain-map \
      --what "Shared context map for this repo or workflow." \
      --how "Captures what humans and agents need to know before working here."
    ```

    This creates a durable topic in Driftless Cloud.
  </Step>

  <Step title="Add structured context">
    Enrich the topic with decisions, gotchas, invariants, and required checks:

    ```bash
    driftless context update onboarding-context \
      --gotcha "WorkspaceGuard is global — use @Public() only for explicit public routes" \
      --decision "RS256 keys for JWTs so services verify without shared secret" \
      --invariant "All routes require auth unless explicitly marked @Public()" \
      --check "Verify role decorator matches the guard's expected metadata"
    ```
  </Step>

  <Step title="Add relations">
    Connect topics to each other with typed edges:

    ```bash
    driftless context update onboarding-context \
      --rel relates_to:api-and-auth-architecture

    driftless context relations onboarding-context
    ```

    Relation types: `relates_to`, `depends_on`, `supersedes`, `blocks`, `implements`, `documents`, `risk_for`.
  </Step>

  <Step title="Get topic as JSON">
    Retrieve the topic in machine-readable format:

    ```bash
    driftless context get onboarding-context --json
    ```

    Agents use JSON output by default. Use `--human` for readable output.
  </Step>

  <Step title="Anchor to file paths">
    Anchor topics to code paths for drift tracking and file-matched loading:

    ```bash
    driftless context update onboarding-context \
      --pattern "apps/*/src/**" \
      --pattern "docs/**" \
      --pattern "AGENTS.md"
    ```

    The CLI validates each pattern against your local checkout. A pattern that matches zero files is blocked; one that matches over 100 files gets an over-broad warning.

    Anchors make topics appear automatically in `context get --files` and `context get --diff`.
  </Step>
</Steps>

## Verify setup

```bash
driftless doctor
driftless context doctor
```

`doctor` checks the API key, workspace, Git remote, and AGENTS.md installation. `context doctor` audits the topic layer (stale / orphaned / zombie / draft topics).

## Working with existing topics

If this repo is already connected to Driftless Cloud, pull the latest state before working:

```bash
driftless sync
```

Then load context for the files you are about to edit:

```bash
driftless context get --files "src/auth/guard.ts,src/auth/service.ts"
```

## Topic-first workflow

Driftless works without a repo scan. The default workflow is:

1. **Create** topics for what you know — decisions, gotchas, invariants, runbooks.
2. **Anchor** topics to code paths when ready — patterns like `src/auth/**`.
3. **Connect** topics with relations — `depends_on`, `relates_to`, `supersedes`.
4. **Grow** coverage through the PR bot — every PR comment tells you which files are unanchored and suggests next steps.
