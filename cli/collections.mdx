title: 'CLI: Collections and contact Records'
description: 'Use the CLI to inspect CRM Collections, work existing contact Records, and manage the explicit lifecycle.'
---

The CLI exposes the operational Collection/Record substrate. In the current commercial product, a Record is a person the workspace has explicitly acquired and filed; do not use this page as permission to create a company account from market evidence.

## Inspect Collections

```bash
driftless collection list
driftless collection get <collection-id> --view full
driftless collection records <collection-id> --limit 25
```

Reads are bounded. Follow the returned cursor instead of assuming that one page is complete. Use `--json` for machine output.

## Work an existing contact Record

```bash
driftless collection record update <collection-id> <record-id> \
  --status contactado \
  --fields '{"next_action":"Reply with the reviewed offer"}'
```

A status must match the Collection's configured lifecycle. `history` and `schedule_activity` are separate explicit operations.

## File an acquired person

For a customer-facing CRM flow, a revealed or imported contact is filed through the people/contact path and the appropriate contact Collection. The CLI's lower-level collection commands do not turn a company, tender, award, or supplier row into a contact Record by accident; use the current acquired-contact path and verify its output.

## Lifecycle

`archive` and `restore` are explicit and reversible. `purge` is permanent, owner/admin only, and should be previewed with the current dry-run/version contract before execution. Record deletion is also a separate operation; never confuse it with changing a status.

## MCP and REST

The public MCP surface uses `collection_query`, `crm_record`, `crm_collection`, and `people_file`. It does not use the retired generic `driftless_collection` or `driftless_entity` tools as a new-integration contract. REST and the CLI may retain lower-level compatibility routes for active technical consumers.
