title: 'Governance'
description: 'A topic is reviewed only if approved. Agents propose, humans approve.'
---

Driftless governs **understanding** the way GitHub governs code. A topic is not "the truth" the moment anyone writes it — it becomes Institutional Context only when a human approves it. That distinction is what makes the context an agent receives trustworthy instead of a wiki that rots.

## Everything is one topic that evolves

There is a single primitive — a **topic** — and it matures along one trust axis. The names are stages of the *same object*, not different types:

```text
Note  →  Proposal  →  Institutional Context     (+ Archived)
(draft)   (proposed)   (reviewed)
```

- **Note** — your private scratch. Only you see it; it's excluded from search; untouched notes auto-archive after ~14 days (recoverable). Think here.
- **Proposal** — a Note promoted for review. Pending a human's vouch; lives in the Proposals queue and can be sent back with a reason.
- **Institutional Context** — the final evolution. A human approved it, so it joins the team's **living, code-anchored knowledge graph** — the multi-context map of the whole codebase. This is the durable truth an agent consumes.

`reviewed` topics carry `governance.authoritative: true` + `approved_by`/`approved_at`. Internally the status enum stays `draft`/`proposed`/`reviewed`/`archived`; the names above are the product language.

The model is **agents propose, humans approve**. `approve`, `reject`, and `merge` require a human identity — an ownerless agent key can propose, but never bless.

```bash
driftless context propose <slug>     # Note → Proposal
driftless context approve <slug>     # → Institutional Context
driftless context reject <slug> --reason "..."   # → Note (with feedback)
driftless context archive <slug>     # retire it
```

## Three surfaces

The dashboard mirrors the three stages: **Context** (the Institutional Context graph — reviewed only), **Proposals** (the approve/reject queue + re-review of drifted context), and **Notes** (your private workspace, with share controls and "expiring soon").

## Who can vouch — project roles

Vouching authority is the **project**, not the workspace. Each member of a project carries a role (CODEOWNERS-for-knowledge):

| Role | Can |
|---|---|
| `contributor` | Read + **propose** (create signals) |
| `maintainer` / `owner` | …+ **vouch** — approve, merge, reject, archive, and clear drift |

In a **private** project, `approve`/`merge`/`reject`/`archive` (and re-vouching a drifted topic) require the `maintainer` or `owner` role — a contributor proposes but does not bless. **Public** and unassigned topics stay open to any human workspace member. Only an `owner` can grant the `owner` role, and a project's last owner can't be demoted or removed. Manage roles in the dashboard's project members panel.

Permissions gate **vouching and visibility only — never coding**. Driftless informs; it never blocks a developer from writing code.

## The trust signal

The whole point of approval is that the agent can tell **truth from hint**. Every `context get` carries it in the canonical response:

```json
{
  "classification": { "status": "reviewed" },
  "governance": { "reviewed": true, "approved_by": "u_cto", "approved_at": "..." }
}
```

An agent should consume `reviewed` topics as truth and `draft`/`proposed` ones as suggestions. Governance without the agent consuming this signal would just be a wiki.

## topic-PR — changing approved truth

Don't overwrite an approved topic. To change canonical truth, open a **topic-PR**: a proposed content change that a human reviews and merges.

```bash
driftless context pr <slug>                                     # list open proposals
driftless context pr <slug> --open --summary "why" --content @new.md
driftless context pr <slug> --merge <id>                        # apply + re-approve (human)
driftless context pr <slug> --reject <id>                       # close without applying
```

A proposal carries a **content patch** (whitelisted to content fields — it can never forge approval or move a topic between projects). Merging applies the patch and makes the topic reviewed again, attributed to the approver.

## Why deterministic

Approval is a human act; everything around it is deterministic and auditable — who approved what, when, and what changed (version + history). A CTO governing context can always answer *"why did the agent trust this?"* with a precise record, not a model's guess.

<Note>
In a future release, platform agents (drift, freshness) will **propose** topic-PRs automatically. They plug into the same proposal queue — humans still approve. The authoring of intelligent proposals is the only piece that waits.
</Note>
