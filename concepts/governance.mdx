---
title: 'Visibility & sharing'
description: "A Cerebro document is born shared with the workspace. Private is a per-document toggle, a public link is one command, and there is nothing to approve."
---

Cerebro is markdown **documents in folders**. A document is born **shared with the workspace** — there is no review queue, no approval, no Note-vs-Knowledge axis. The only trust is that it's in Cerebro. What used to be governance is now two much smaller things: who can see a document, and who can change it.

## A document is born shared

There is one primitive, a **document**: `<folder>/<name>.md`, where the folder is a knowledge area and `<folder>/Structure.md` says what that area is for. Write it and it is the team's — visible to every member of the workspace, retrievable by every agent, immediately.

```text
context write  →  the document is in Cerebro  →  every member and agent reads it
```

- **Shared** (the default): every workspace member sees it, search returns it, `context_retrieve` ranks it.
- **Private** (`--private` on the CLI, `is_private` on the API/MCP): a per-document toggle. Only its author sees it, and it is excluded from search until they share it. It is a switch, not a stage to graduate from — `--public` flips it back.
- **Public link**: a read-only URL anyone can open without logging in. Opt-in per document, revocable at any time.

There is no `proposed`, no `reviewed`, no approval queue. The `status` field still exists on the wire and is **inert** — nothing reads it as authority.

To change a document, read it and rewrite it. `context write` replaces the whole body, so the honest move is read → fold the new fact in → write back.

```bash
driftless context read billing/refund-flow.md > refunds.md
driftless context write billing/refund-flow.md --content @refunds.md
driftless context write billing/refund-flow.md --content @refunds.md --private
driftless context share refund-flow            # public read-only link
driftless context share refund-flow --revoke   # revoke it
```

## The customer surface

The dashboard's customer-facing document surface is **Cerebro**: the folder tree and its markdown documents. The commercial CRM is a separate contact-first surface under Prospectos. Comments and the retired topic graph are not part of the current customer navigation.

## Who can change what: workspace roles

Membership is what grants access. Each member carries one role:

| Role | Can |
|---|---|
| `member` | Read every shared document + write and rewrite documents |
| `admin` / `owner` | …+ manage members, move documents between workspaces, and delete |

Writing is not gated: a member writes and rewrites documents directly. Only an `owner` can grant or revoke the `owner` role, and the last owner can't be demoted or removed. The workspace creator is the first owner; manage roles in **Settings → Members**.

Permissions gate **visibility and administration only, never coding**. Driftless informs; it never blocks a developer from writing code.

## What the agent reads

An agent doesn't weigh a trust level any more — it reads what's there. Every `context get` still carries the document's identity and freshness, which is what actually matters:

```json
{
  "classification": { "status": "draft" },
  "stale": { "is_stale": true, "stale_reason": "anchored code changed" }
}
```

Treat `stale` as the signal worth acting on: the document was true and the code moved. `status` is a historical field; ignore it.

## Retired: the Note → Knowledge governance

`propose`, `approve`, `reject`, `archive`, `ack`, `unvouch` and `pr` (Suggested edits) are **retired**. They remain on the CLI and the API as **no-ops** so an older agent or script gets a clear answer instead of an error, and each one prints the same line before exiting 0:

```bash
driftless context propose <slug>   # → Los documentos de Cerebro no necesitan
driftless context approve <slug>   #   aprobación; edítalos con
driftless context pr <slug>        #   `driftless context write`.
```

Don't call them. If a document needs to change, rewrite it — that's the whole workflow now, and it's the same one whether you're a person or an agent.

## Why deterministic

Nothing about this is less auditable. Every write bumps a version and appends a history event: who wrote it, when, and what changed. A CTO can still answer *"why did the agent trust this?"* with a precise record — the record just no longer includes an approval step nobody was running.

<Note>
Documents that were `reviewed` before the retirement kept their content and their history; only the badge went away. Nothing was archived or deleted in the migration.
</Note>
