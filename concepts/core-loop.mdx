---
title: 'The Driftless loop'
description: 'Create, observe, deliver, and check.'
---

The Driftless loop has four phases. Every command and event fits into one of them.

## Phase 1: Create

Start with topics — durable engineering memory. Create what you know:

```bash
driftless context add "auth-flow" \
  --what "JWT validation and role-based access control" \
  --how "RS256 asymmetric keys, guard decodes, role decorator checks" \
  --pattern "src/auth/**" \
  --tags auth,security \
  --kind code-context

driftless context update auth-flow \
  --decision "Chose RS256 over HS256 so services can verify without shared secret" \
  --gotcha "Token refresh is NOT handled by this guard; see [[token-refresh]]" \
  --rel depends_on:token-refresh
```

## Phase 2: Observe

The GitHub App watches pushes and PRs. On every push to a tracked branch, it matches changed files against all workspace topics. Any topic whose anchored patterns overlap with the changed files gets marked **stale** with a human-readable reason.

On PRs, the bot posts a sticky comment listing matched topics and the coverage breakdown: how many files in the PR are covered by a topic, how many are outside any topic, and which files are unanchored — along with suggested next steps to close the gap.

Pushes to tracked branches can mark topics as stale. PRs themselves do not trigger staleness; they trigger observation only.

See [PR Bot](/concepts/pr-bot) for how coverage feedback works.

## Phase 3: Deliver

Context reaches agents and humans through CLI commands:

```bash
driftless sync                              # what drifted since you last looked
driftless context get auth-flow              # full context for one topic
driftless context get --diff                # context for your current local changes
driftless context get --files "a.ts,b.ts"  # topics matching specific files
```

`context load` also works but is deprecated — prefer `context get --files`.

## Phase 4: Check

When code changes on tracked branches, topics whose anchored patterns overlap get marked stale. The staleness reason lists the specific files and commit that triggered it.

```bash
driftless sync                    # shows stale topics alongside other changes
driftless context doctor          # full health audit: staleness, zombie, orphaned topics
driftless context get --diff      # staleness status for your current local changes
```

`context doctor` audits the topic layer itself — it flags `stale`, `orphaned` (repo deleted), `zombie` (anchor patterns no longer match any file), `draft` (suggested, never confirmed), and `docs_pending` topics.
