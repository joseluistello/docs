---
title: 'Authentication & Authorization'
description: 'How Driftless handles auth — API keys, Clerk, and workspace isolation.'
---

Driftless has two authentication paths, both resolving to the same workspace identity. All actions are scoped to the authenticated workspace — cross-workspace access is rejected at the API layer.

## Authentication paths

### 1. API Keys — CLI and programmatic access

Header: `X-API-Key: drift_xxx`

- Keys must start with `drift_`
- Validated via SHA-256 hash lookup in the database
- Scoped to the workspace that generated the key
- Raw key is shown **once** at creation time and never stored

### 2. Clerk — Dashboard and browser access

Header: `Authorization: Bearer <token>`

- Requires Clerk organization membership
- Workspace is resolved from the Clerk organization ID
- Auto-creates a workspace on first access if the Clerk org matches
- Dashboard uses `credentials: include` for cookie-based session management

## Workspace isolation

Every API endpoint resolves workspace identity from the auth credential. The URL `:slug` parameter is verified against the authenticated workspace. If a request targets a different workspace's resources, the API returns `403 Forbidden`.

```typescript
// All guarded endpoints follow this pattern:
const workspace = await this.resolveWorkspace(auth);
if (workspace.slug !== params.slug) {
  throw new ForbiddenException('Cross-workspace access denied');
}
```

## Rate limiting

| Limit | Scope | Rate |
|---|---|---|
| Webhook | Per IP | 100 / minute |
| Public | Per IP | 30 / minute |
| Authenticated | Per key or session | 200 / minute |

Rate limits are IP-based and enforced at the global middleware level before reaching route handlers.

## Public endpoints

Only 6 routes are exempt from authentication:

| Route | Purpose |
|---|---|
| `GET /health` | Health check |
| `GET /version` | API version |
| `POST /webhooks/github` | GitHub webhook receiver |
| `POST /webhooks/clerk` | Clerk webhook receiver |
| `POST /workspaces` | Initial workspace creation |
| `GET /blog/*` | Public blog content |

Everything else requires authentication via API key or Clerk token.

## API key lifecycle

| Stage | What happens |
|---|---|
| **Create** | Raw key generated, returned once. SHA-256 hash stored. |
| **List** | Only key prefixes shown (first 8 chars). Raw keys never exposed. |
| **Revoke** | SHA-256 hash deleted. Key immediately invalid. |

<Warning>
  If you lose a raw API key, you cannot recover it. Generate a new one and revoke the old prefix.
</Warning>

## Dashboard auth flow

Clerk sign-in → organization selection → workspace lookup (or auto-create) → JWT token for API calls. All dashboard API requests include `Authorization: Bearer <clerk_token>`.
